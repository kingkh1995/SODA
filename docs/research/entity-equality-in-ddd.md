# 实体相等性在 DDD 一手文献中的裁定依据

> **结论摘要**
> - **Evans《Domain-Driven Design》 (2003) 从未讨论 Java 层面的 `equals`/`hashCode`**：全书正文零次出现 `hashCode`，`equals`
    仅出现在 JUnit `assertEquals` 代码示例中；ENTITY 模式的相等性主张停留在 **模型语义层**（"The model must define what it
    means to be the same thing."）。因此「实体必须/不必实现 `equals`」在 Evans 书中 **不存在直接主张**——既非要求，也非禁止。
> - Evans 把「对象引用相等」明确 **降级**，而非推荐：他写「O-O 语言的 identity 操作…… **在其他应用领域意义很小**
    」，且内存引用身份「在持久化/网络传输中 **丢失**」。项目印象中的「Evans 说过引用/对象身份足够」—— **未能在原文中找到该句**
    （见 §6 证据缺口 G2）。
> - **Vernon《Implementing Domain-Driven Design》 (2013) 明确主张实体应基于 identity 实现 `equals`/`hashCode`**，并
    **偏好**该方案优于「按属性值比较」；二者他都在讨论， **「完全不重写」不在他的选项集中**。这是本议题最直接的反方一手证据（§5.1）。
> - Vernon 的偏好有明确触发条件： **实体进入 `java.util.Set`** 且 identity 尚未分配。项目若不存在该用法，其反方强度下降为「未覆盖场景的默认倾向」，而非「无条件要求」。
> - **JPA 规范只要求主键类（composite PK / id class）与用作 map key 的 embeddable 实现 `equals`/`hashCode`
    ，从未要求实体类重写**； **现行 Hibernate ORM User Guide 反过来明说「除少量特定场景外，你可能应考虑完全不实现 `equals`/
    `hashCode`」**——两项外部权威与项目决定 **方向一致**（§5.2、§5.3）。
> - **「Comparable」在 Evans 与 Vernon 两本书中都不是对实体的要求**：Evans 全书 `Comparable` 零命中（仅作英文形容词出现），Vernon
    全书零命中；相反，Evans 的 CLOSURE OF OPERATIONS 明确「这类机会多半落在 VALUE OBJECTS，而不是
    ENTITIES」。「可比」是值对象/标识符侧的性质（§4）。
> - **一致性判定：部分一致（需限定条件）**——Evans（无主张）、JPA、Hibernate 支持；Vernon 的 **首选方案相反**，但其 **触发前提**
    （实体进 Set、id 未分配）恰是「不重写 + 显式 id 比对」天然规避的（§5.5）。

## 2. Q1 — Evans 2003 对 Entity 的定性与相等性

**章节定位**：第 5 章 *A Model Expressed in Software*（手稿第 5 章），模式块 **ENTITIES (A.K.A. REFERENCE OBJECTS)**（手稿

1.3 两句（ **不是**某些二手材料转述的「identity 比 attributes 更重要」这类泛化句）。

### 2.2 Evans 是否讨论实现层面的 `equals`/`hashCode`？

| #   | 断言                                                                              | 证据                                                                     | 英文原句 / 事实                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
|-----|-----------------------------------------------------------------------------------|--------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1.6 | **Evans 全书未出现 `hashCode` 一词**                                              | 全文机械扫描（手稿 PDF 抽取文本，去空白后匹配 `hashcode` / `hash code`） | 命中 **0**。（仅 2 处 `hash` 为英文动词 "hashed out" 与 "hash tables" 的比喻）                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 1.7 | `equals` 仅出现在 JUnit 断言示例中，无一处是对象相等性设计的讨论                  | 全文扫描 `equals`                                                        | 命中 11 处，**全部**为 `assertEquals(...)` 测试代码（Paint 混合、NetRule 等示例）                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 1.8 | Evans 提到语言内建 identity 操作时，是**贬低其在业务领域的适用性**，而非推荐      | Evans (2003) ch.5 ENTITIES                                               | "The issue of identity is confused by the fact that object-oriented languages build "identity" operations into every object (e.g. the '= =' operator in Java). | 1.9 | Evans 进一步指出内存引用身份在持久化/分布式传输下**会丢失**，故不足以承载实体身份 | Evans (2003) ch.5 **Designing the Identity Operation**                   | "Object-oriented languages have "identity" operations that determine if two references are to the same object by comparing their location in memory, but **this kind of identity is so fragile that, in most technologies for persistent storage of objects, every time an object is retrieved from a database a new instance is created, and so this identity is lost.** Every time an object is transmitted across a network, a new instance is created on the destination, and this identity is lost."（手稿 p.68） |

**判定（1.6–1.9）**：

- 1.6、1.7 是 **可复核的事实**：Evans 2003 对 `equals`/`hashCode` **无任何实现层主张**—— **既未要求实体重写，也未禁止**。任何以
  Evans 名义主张「实体必须实现 equals」或「实体只应引用相等」的说法，都 **不是**出自本书原文。
- 1.8、1.9 是 **【作者明确主张】**：对象引用相等（`==`）在 **业务领域内意义很小**、「fragile」且在存储/传输后丢失。这 **否定**
  了「Evans 认为对象引用足够」的读法（见 §6 G2）。

### 2.3 实体身份应如何表达：Evans 的答案是「一个 identified attribute / ID symbol」

| #    | 断言                                                                                                                                  | 来源                                                   | 英文原句                                                                                                                                                                                                                                                                                                                                                   |
|------|---------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

**判定（1.10–1.13）**： **【作者明确主张】**。「操作性地确立身份」是模型层要求（1.10）；Evans 给的两条实现法是「自然键」与「唯一 ID
符号」（1.11）， **未提**对象 `equals`/`hashCode`。1.12 说明他把「写一个比较操作」视为实现细节，其正当性
**取决于是否对应领域中的有意义的区分**——这与「相等语义必须由模型显式定义」的立场一致，但 **不支持**也 **不排除**任何特定
Java 实现。

## 5. Q4 — 反方证据与冲突点

### 5.1 反方一（最强）：Vernon 本人主张实体应基于 identity 重写 `equals`/`hashCode`

- **主张原文**（IDDD ch.5 §When the Timing of Identity Generation Matters, **p.186**）：
  > "It is more desirable for Entities to have equals () and hashCode () methods that are based on the object's unique
  identity rather than other attributes."
- **其触发前提**（同上 p.185）：实体 **进入 `java.util.Set`** 且 **identity 尚未分配** → 若以 identity 实现 `equals`
  ，多个新实体会被 Set 吞并；不以 identity 实现则需退化为属性相等。
- **实践佐证**：IDDD_Samples 中 20 个 Entity 子类手写 identity-based `equals`（§3.6）。
- **与本项目决定的关系（冲突点）**：
    - 项目决定「完全不重写 `equals`/`hashCode`（继承 `Object` 引用相等）+ 显式按主键 id 比对」 **不等于 Vernon 的首选**
      （首选是重写、且以 identity 为判据），也 **不等于**他的次选（属性值相等）。
    - 但 Vernon 的 **问题成因**（延迟分配的 identity 导致 Set 吞并）在「不重写」下 **不会发生**：引用相等下两个新实体天然不等（各自入
      Set），同一实例重复添加天然被 Set 去重（引用相等即相等）。Vernon 未讨论这一路径，因此这是 **未覆盖场景**
      下的默认倾向，而非对「不重写」的反驳。
    - **真正需要条件的冲突点**：Vernon 的用意之一是「 **同一逻辑实体的两个实例**（如跨 Session/跨聚合加载）应当相等」。引用相等下此语义
      **消失**；项目以「显式按 id 比对」补足——但这要求 **每一处需要逻辑相等的调用点都显式比对**，属于
      **语义面收窄换来的实现义务**。当前代码中 `User.addAccount` 用 `accounts.contains(account)` 并注释「已包含同一实例时
      no-op」，其语义 **已是引用相等**，随后以 `findAccount(account::typeEquals)` 承担逻辑重复判定——属与「不重写」 **相容**
      的既有写法（本次只读核对：`soda-user/soda-user-domain/.../User.java:197`）。

| 4.10 | `equals`/`hashCode` 的强制仅在**复合主键类**上                                              | JPA 3.2 **§2.4.1 Composite primary keys**                         | "**The primary key class must define `equals` and `hashCode` methods.** The semantics of value equality for these methods must be consistent with the database equality for the database types to which the key is mapped." |
| 4.11 | 另一处强制：embeddable 作 **map key** 时「必须实现 `hashCode` 与 `equals`，且与映射列一致」 | JPA 3.2 **§2.9.1 Map Keys**                                       | "If an embeddable class is used as a map key, **the embeddable class must implement the `hashCode` and `equals` methods consistently with the database columns** to which the embeddable is mapped."                        |
| 4.12 | 规范层「实体相等」定义为**同主键值**（JPQL 比较语义），与 Java 方法无关                     | JPA 3.2 **§4.6.14 Equality and Comparison Semantics**             | "**Two entities of the same abstract schema type are equal if and only if they have the same primary key value.**"                                                                                                          |
| 4.13 | 主键值**不得**在持久化后修改                                                                | JPA 3.2 §2.4                                                      | "The application must not change the value of the primary key of an entity instance after the instance is made persistent."                                                                                                 |

**判定**：与项目决定 **方向一致**且 **强化其依据**——规范要求的 `equals`/`hashCode` 落点正是 **标识符/主键类**
（4.10、4.11），本项目 `Identifier` 族（`AuthAccountId` 等 DP）恰好重写了基于规范值的相等性；而 **实体类**在规范中无此要求（4.9、4.12
把实体相等定义为 **PK 值相等**，即「显式按 id 比对」）。（4.12 的适用范围是 JPQL 查询语义， **不可**直接外推为 Java `equals`
规范；本条只用于说明规范把实体同一性锚定在主键上。）与 5.2 并置可见： **JPA 规范 ≠ Hibernate 建议**；前者不要求，后者在某些场景下建议。

## 6. 与本项目决定的一致性判定

**待判定的项目决定**： **领域 Entity/聚合不再重写 `equals`/`hashCode`（继承 `Object` 的引用相等）；需要「含已有」等查找语义时，显式按主键
id 比对。**

### 6.1 逐条判定

| 判定维度                 | 结论                           | 依据                                                                                                                                                                                                                                                                         |
|--------------------------|--------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Evans 2003 一致性        | **一致（因无主张，故无冲突）** | Evans 全书不涉 `equals`/`hashCode`（1.6–1.7）；其模型层要求是「identity 优先、须能区分、须定义何为同一物」（1.2、1.4、1.10），项目以「主键 id 显式比对」满足「定义何为同一物」这一要求；Evans 明确否定引用身份**足以**承载业务身份（1.9），但**未**要求以 Java `equals` 承载 |
| Vernon 2013 一致性       | **部分一致（需限定条件）**     | Vernon **首选** identity-based `equals`/`hashCode`（2.5）→ 与「不重写」相反；其**次选**为属性值相等（2.4）→ 亦不同。但他论证的前提（实体进 Set + id 未分配；跨实例比对）(i) 在引用相等下不复现，(ii) 项目以显式 id 比对补足「同一逻辑实体」语义。逐条限定见 6.2              |
| JPA 规范一致性           | **一致**                       | 规范只要求主键类（4.10）与 embeddable-as-map-key（4.11）实现 `equals`/`hashCode`；实体相等被定义为**同主键值**（4.12）；实体类无重写义务                                                                                                                                     |
| Hibernate 官方文档一致性 | **一致（附条件）**             | 现行 User Guide：「除 identifier 类等少数场景外，可考虑完全不实现」（4.4）；其条件侧建议（脱离 Session / 进 Java 集合，4.6）当前不成立。历史 3.3 的合取条件（Set 关联 且 detached 重挂，4.1）当前亦不成立                                                                    |
| 「可比较」面一致性       | **一致**                       | 两书对实体无 Comparable 要求（3.1–3.2、2.13–2.14）；Evans 把可组合/可计算性指向值对象（3.3）。项目把 `Comparable<Self>` 限定在 `Identifier`（值对象侧，3.12）与文献定性一致；但该要求本身无 DDD 一手依据（§7 G5）                                                            |

**总判定：部分一致，需限定条件。**

### 6.2 限定条件（决定成立所需的前提）

1. **领域实体不得进入基于 `hashCode` 的集合或作为 hash key**（`HashSet` / `HashMap` / `Set` 去重）。引用相等下这些结构的去重语义退化为「同一实例」，与
   DDD 语境下「同一实体」的直觉不同；Hibernate User Guide（4.6/4.8）与 Vernon（2.3）指向的正是这一面。当前项目满足（本次只读核对：域内无实体
   hash 集合；`User.accounts` 为 `List<AuthAccount<?>>`）。
2. **「同一逻辑实体」的判定必须在每一处调用点显式按主键 id 表达**，包括测试断言。本次只读核对到 7 处序列化/恢复测试以对象值相等断言
   round-trip（`UserTest:763,772,781,790,799`、`VerificationTest:142`、`SocialAuthAccountTest:143`），以及各聚合
   `@Nested 相等性` 组；这些断言的现有语义在「不重写」下 **不再成立**，其原本承载的「字段/参数漂移检测」需要在调用点以显式字段比对（或逐字段断言）重建。
3. **不得引入 JPA 实体集合关联（`@OneToMany`/`@ManyToMany`/`@ElementCollection`）或 detached 重挂路径**。Hibernate 3.3 §4.3
   的合取条件即由这两者构成（4.1）；一旦引入，「不重写」将与该官方要求正面冲突。当前项目不满足（本次只读核对：PO 无任何关联映射注解）。
4. **Evans 层面无可援引的「引用相等足够」依据**：Evans 实际写的是引用身份在业务领域「意义很小」且在存储/传输后丢失（1.8–1.9）。因此该决定
   **不可**以「Evans 说过引用相等足够」立论；其正当依据应落在「 (a) 相等语义由模型显式定义（1.4/1.12）＝ 显式 id 比对； (b) JPA
   规范把实体相等锚定在主键（4.12）； (c) 现行 Hibernate 明确许可不实现（4.4）」。

### 6.3 与「值对象侧」的对照（项目内一致性）

- 项目的 **值对象/标识符**侧（`Identifier` 族、DP 族） **保留**基于规范值的 `equals`/`hashCode`，并强制 `Comparable<Self>`
  （3.12）。这与文献对 **值对象**的要求一致：值对象无身份、可互换，故必须以值相等定义同一性（3.5–3.7、3.9–3.10）。即本项目实际落成的是文献所描述的分工形态：
  **值对象/标识符 = 值相等（并可比）；实体 = 身份语义（以主键显式表达）**——差异仅在 **实体的身份语义不由 Java `equals` 承载**
  ，而由每次显式比对承载。
- 该分工与 Evans 的 VALUE OBJECT「what 而非 who」（3.5）与 ENTITY「须能区分同属性对象」（1.2）的二分逐条对应。
